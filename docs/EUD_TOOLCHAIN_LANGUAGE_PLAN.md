# EUD 도구 동봉 및 다중 언어 확장 개발 계획

**2026-10-04 계획 확장:** 일반 트리거도 epScript/Python/Lua 중 선택한 언어로
편집하고 검증된 공통 범위에서 언어를 전환하는 계획을 §7에 추가했다.
계획 수립만 완료했으며 구현은 아직 없다. X1~X5 완료 기록을 변경하지 않는다.
Lua는 공식 euddraft 입력 언어가 아닌 앱의 제한 변환 대상이다.

구현했다. [최신 기록](EUD_BUNDLED_TOOL.md). 깨끗한 Windows·ACL·차단망 배포 인수가
남아 X1 전체는 진행 상태다. 아래 최초 계획과 날짜별 메모는 이력으로 읽는다.

2026-09-15 사용자 요청으로 초안을 작성하고 2026-09-16 정리했다. 최초 계획 중 도구 동봉·생성 빌드는 구현했고 Python entry·Lua는

M8의 패키징 기준을 재사용한다. 추정 일정 대신 단계별 완료 조건으로 진척을 판단한다.

## 1. 목표와 현재 상태

목표는 사용자가 별도 Python/euddraft 설치 없이 앱에서 EUD 맵을 빌드하고,
설정 UI·epScript·Python 및 후속 Lua 중 적절한 작성 방식을 선택하게 하는 것이다.

| 항목 | 현재 | 목표 |
| --- | --- | --- |
| 도구 제공 | 관리형 동봉 기본값·명시적 외부 선택 구현 | 검증된 도구 동봉 기본값 + 외부 경로 선택 |
| 설정 UI | 61개 후보 필드·실행 규칙 편집/생성/테스트 빌드 | 검증된 필드의 결정적 생성·실제 게임 적용 |
| epScript | 기본 빌드 프로필 `.eps` | 기존 호환 유지, 생성 모듈과 사용자 코드 조합 |
| Python | 도구 내부 기반, 앱의 정식 entry 프로필은 아님 | `.py` 작성·entry·진단·안전 빌드 지원 |
| Lua | 미지원 | 버전이 명시된 EUD용 제한 문법과 변환기 |

현재 allowlist의 euddraft 0.10.2.5와 후보 eudplib 0.80.6은 최초 평가 기준이다.
최신 버전으로 자동 교체하지 않고 실제 배포물/API/게임 검증 후 지원 프로필을 확정한다.
과거 외부 경로 부재와 현재 동봉 도구 제공은 구분한다. 실제 설치 선택은 EUD Tools에서 검사한다.

## 2. 구조와 범위

앱 설치 디렉터리에 버전별 도구 패키지를 포함하고, 빌드는 기존 인터페이스 뒤의
별도 프로세스에서 실행한다. Flutter 프로세스 안에 Python을 임베드하지 않는다.
별도 프로세스는 장애·취소 경계이며 보안 샌드박스가 아니다. 사용자 Python과 플러그인은
임의 실행 코드로 취급하고 기존 실행 신뢰 정책을 유지한다.

```text
설정 UI → 선언적 설정 → 검증된 생성기 ───────┐
Lua 제한 문법 → AST/의미 검사 → 공통 중간 표현 ┤
사용자 epScript / Python entry ────────────┤
                                         ↓
                      생성 wrapper + 고정된 hook 순서
                                         ↓
                  동봉 또는 외부 euddraft (별도 프로세스)
                                         ↓
               임시 출력 → MPQ/CHK 검증 → 새 결과 맵
```

중간 표현은 타입 설정과 후속 Lua 및 §7의 제한된 공통 동작을 위한 것이다. 임의 Python/epScript를
역변환하거나 모든 코드의 충돌을 정적으로 탐지한다고 약속하지 않는다. 프로젝트는
하나의 사용자 entry 언어를 선택하고 앱 생성 모듈을 조합한다. 언어 간 자유로운 상호
import/콜백은 첫 버전에서 지원하지 않는다. 기존 사용자 entry는 덮어쓰지 않는다.

Lua 연구는 가능하지만 사용자에게 Lua 지원을 노출하는 것은 X4 인수 이후다.

외부 Python 패키지 지원은 고정 의존성·라이선스·설치 정책을 정한 후 확장한다.

### X4. Lua 기반 EUD 제한 언어

Lua 엔진으로 스크립트를 실행하는 것만으로 게임의 EUD 동작이 생성되지는 않는다.
첫 접근은 파싱 및 의미 분석으로 제한된 코드를 변환하는 것이다. 지원 버전·문법은
프로토타입 후 ADR로 확정하고, 일반 Lua 전체 호환이나 Lua VM의 맵 내 실행을 표방하지 않는다.

§7의 L4는 일반 TRIG용 Lua 읽기/쓰기 단계이며 이 X4의 EUD 변환 완료와 구분한다.

- [ ] Lua 문법 버전과 EUD 전용 API, 빌드 시 값/게임 중 값의 구분 명세.

## 7. 일반/EUD 공통 다중 언어 편집 및 전환 계획

### 7.1 목표와 현재 구현 근거

이 절은 2026-10-04 사용자 요청에 따른 개발안이며 구현 완료나 출시 약속이 아니다.

### 7.2 제품 계약: 세 언어, 두 모드, 두 작성 범위

| 구분 | 동작 | 언어 전환 |
| --- | --- | --- |
| 일반 / 공통 작성 | 지원 조건·액션·소유자·플래그의 제한 선언 문법 -> TRIG | 모델로 해석 가능한 범위만 세 언어 전환 |
| EUD / 공통 작성 | 검증된 변수·식·실행 hook/API -> EUD 코드 생성 -> 빌드 | 인수된 공통 범위만 세 언어 전환 |
| EUD / 자유 작성 epScript·Python | upstream 함수/import 등 사용자 코드 -> 기존 도구 실행 | 자동 변환 없음. 파일 보존·별도 entry 선택만 제공 |
| Lua 전체 언어 / 임의 타 언어 코드 | 최초 지원 대상 아님 | 미지원 위치·이유 표시, 생성/적용 거부 |

공통 작성은 각 언어의 실제 문법 중 제한된 부분과 버전형 맵 API를 사용한다.
전체 언어 호환, 임의 epScript/Python/Lua의 상호 번역을 표방하지 않는다.
epScript 공통 API는 upstream에서 파싱되는지 검증하고 생성 wrapper/import를
명시한다. 유사한 자체 문법을 `.eps` 정식 호환으로 표시하지 않는다.

일반 모드 최초 범위는 명시적 트리거 선언과 리터럴 인자다. 게임 중 변수·루프·
일반 `if`를 임의 Deaths 카운터/스위치로 바꾸지 않는다. 후속 생성 시 반복은
정적 유한 전개로 명시하고 게임 중 반복과 구분한다. OR 조건의 트리거 복제로
액션이 중복 실행될 수 있으므로 최초 범위에서는 자동 변환하지 않는다.
`Wait`, `Preserve Trigger`, 플레이어 실행 순서, 조건/액션 순서·비활성 슬롯을
유지한다. 일반 지원 범위를 넘으면 EUD 필요 이유를 표시하며 자동 승격하지 않는다.

### 7.3 파이프라인과 데이터 보존

```text
일반 트리거 목록 <-> 기존 typed 모델 / 원시 바이트 스냅샷
                                      |
epScript / Python / Lua -> 파서 -> 의미 검사 -> 버전형 공통 모델
                                      |               |
                             일반 TRIG 변경안      EUD 실행 모델
                                      |               |
                              명시적 적용/Undo    epScript/Python 생성
                                      |               |
                                  Save As       기존 안전 EUD 빌드

검증된 공통 모델 -> 선택 언어 formatter -> 새 소스 + 원본 위치 매핑
```

단일 거대 IR로 TRIG와 임의 EUD 코드를 표현하지 않는다. 일반 레코드 모델과
EUD 실행 모델은 분리하고 타입 인자/리소스 참조/진단·source map만 필요에 따라
공유한다. 기존 EUD 규칙 모델을 조사하고 재사용 가능성을 L0에서 확정한다.

- 일반 맵의 원시 TRIG가 적용 전 기준이다. 초안은 기준 document revision/
  fingerprint에 묶고 적용은 한 Undo 명령으로 원자적으로 수행한다.
- 레코드·슬롯 순서, owner 원시 값, execution/slot flags, 패딩·예약 바이트를
  유지한다. 빈 슬롯을 압축하지 않고 수정한 인자만 변경한다.
- raw/EUDX/미지원 슬롯은 읽기 전용 참조로 표시하고 기존 바이트를 복사한다.
  token은 기준 스냅샷에 귀속시켜 임의 raw 주입/다른 맵 재사용을 거부한다.
  미지원 블록 삭제는 명시적 확인과 Undo를 요구하고 자동 삭제하지 않는다.
- 원시 문자열 ID/바이트를 보존하고 이름 중복은 숫자 ID로 구분한다. 자동 합치기/
  인코딩 변경은 금지한다. 신규 문자열은 기존 리소스 명령과 묶는다.
- 언어 전환은 파싱/지원 검사 -> 의미 동등성 검사 -> 미리보기 -> 새 파일 생성
  순서다. 미지원 구문이 하나라도 있으면 부분 변환하지 않는다.
- 공백·주석·변수 이름의 완전 왕복은 보장하지 않는다. 원본 소스/주석은 별도
  유지하고 생성본은 canonical 형식임을 표시한다. 주석 연결 규칙은 L0에서 정한다.
- dirty 초안의 목록 수정/언어·모드 변경은 적용·보관·취소를 선택하게 한다.
  문법 오류·오래된 결과는 적용하지 않고 단순 입력/저장으로 빌드하지 않는다.
- 세 소스를 동시 진실 원본으로 두지 않는다. 적용된 맵과 선택 소스의 기준
  버전을 관리하고 타 언어 문서는 명시적 전환 시 새로 생성한다.

순수 모델·의미 검사·변경 명령은 Domain/Application에 둔다. 파일·외부 파서·
프로세스는 port 뒤 Infrastructure에 두며 UI가 파싱/파일을 직접 호출하지 않는다.
정규식 치환이나 문자열 eval 대신 검증된 AST 도구를 우선한다. epScript의
라이선스/AST 접근성, Python `ast`, Lua 파서의 Windows·라이선스·배포 조건을
L0에서 조사한다. 확정 전 새 의존성을 추가하지 않는다.

### 7.4 언어 의미와 안전 계약

| 차이 | 명세 / 검증 기준 |
| --- | --- |
| 정수 | 일반 인자는 기존 u8/u16/u32 범위 밖이면 거부. 공통 EUD 정수는 u32와 명시 연산으로 정의, signed/overflow/shift/division 검증 후 제공 |
| 참/거짓 | Lua의 0은 참, epScript의 0은 거짓. 공통 조건은 명시 bool/조건식만 허용하고 묵시 truthiness 변환 거부 |
| 배열·테이블 | 공통 API 인덱스 명시. Lua 배열 관습을 그대로 EUD 배열로 복사하지 않으며 혼합 key/nil/hole/동적 table 초기 거부 |
| 문자열·참조 | 내부는 안정적 맵 ID. Lua byte string/Python Unicode/맵 원시 문자열 차이를 암묵 변환하지 않음 |
| 실행 시점 | 선언/정적 전개와 게임 hook 구분. on-start/before/after 및 owner 실행 횟수의 의미를 capability 표로 고정 |
| 평가 순서 | 액션·인자 평가 순서와 short circuit 정의. 의미가 달라지는 기능은 지원 거부 |
| 위치 | Python UTF-8 byte column, Dart editor UTF-16, Lua 파서 위치를 구분, 한글/CRLF/탭 진단 테스트 |

공통 파싱은 사용자 코드를 실행하지 않는다. `eval`/`exec`/동적 import, Lua
`load`/`require`/metatable/FFI/coroutine, 파일·네트워크·프로세스 접근은 거부한다.
AST 파싱만으로 자원 안전성이 보장되지는 않는다. 입력 크기·깊이·노드 수·
전개량·시간·메모리 예산과 취소를 둔다. parser도 별도 작업 경계로 격리한다.
자유 작성 EUD 빌드는 임의 실행 코드이며 신뢰 승인과 기존 도구 무결성 검사/
취소를 유지한다. 별도 프로세스를 보안 샌드박스라고 부르지 않는다.

### 7.7 먼저 진행할 개발 건과 공식 근거

다음 코드 작업은 L0 제한 선언 문법/모델 명세와 세 언어 파서 feasibility다.
성공하면 L1 -> L2로 진행한다. 전체 언어 엔진을 한 번에 구현하거나 기존 사용자
코드를 자동 덮어쓰지 않는다. 의존성/스키마의 최종 결정은 후속 ADR로 남긴다.

2026-10-04 확인한 공식 근거:

- [epScript 문법](https://github.com/armoha/euddraft/wiki/epScript-Basics): JavaScript 계열 문법과 EUD 변수/조건, Python import. 공통 작성 범위는 앱의 추가 제한이다.
- [euddraft 0.10.2.5 로더](https://raw.githubusercontent.com/armoha/euddraft/v0.10.2.5/pluginLoader.py): `.eps`/`.py` 로딩과 세 hook 등록. Lua 직접 입력 경로는 없다.
- [Python 3.13 AST](https://docs.python.org/3.13/library/ast.html): 구문 트리·원본 위치/버전 차이. 문법 버전은 실제 번들에 맞춰 고정한다.
- [Lua 5.4 명세](https://www.lua.org/manual/5.4/manual.html): 0의 truthiness, nil/table/수치·동적 기능. 5.4는 조사 기준이고 최종 지원 버전은 L0에서 확정한다.

이는 언어/로더 사실의 근거이지 앱의 변환 구현 증거가 아니다. 파서 commit/hash·
라이선스는 L0에서 확인하고 변동 브랜치를 지원 프로필의 유일한 근거로 쓰지 않는다.
